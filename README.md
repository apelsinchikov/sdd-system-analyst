## 📖 О чём это

**sdd-system-analyst** — это спецификация работы системного аналитика уровня Senior в формате Spec-Driven Development.

Здесь описано не «что аналитик умеет», а **как именно он работает**: как собирает требования, как проектирует API и БД, как держит границы и статусы, как работает с параллельными задачами и командой. Всё — в виде формальных требований (MUST/SHALL), сценариев и шаблонов, пригодных для использования как человеком, так и ИИ-агентом.

**Философия:** spec-first, code-second. Нет спеки — нет задачи.

## 🗂 Структура репозитория

```
sdd-system-analyst/
├── README.md                          # этот файл
└── openspec/
    ├── project.md                     # контекст, миссия, зона ответственности
    ├── AGENTS.md                      # как работает аналитик: ритуалы, границы, антипаттерны
    ├── specs/
    │   └── senior-analyst/
    │       └── spec.md                # формальные требования к работе (RFC 2119)
    └── changes/
        └── TEMPLATE/
            └── proposal.md            # шаблон любого изменения
```

### Что за что отвечает

| Файл | Назначение | Читается за |
|------|-----------|-------------|
| [`openspec/project.md`](openspec/project.md) | Кто я и что делаю. Контекст, миссия, зона ответственности | ~1 минуту |
| [`openspec/AGENTS.md`](openspec/AGENTS.md) | Как я это делаю. Ритуалы, коммуникация, границы, антипаттерны | ~3 минуты |
| [`openspec/specs/senior-analyst/spec.md`](openspec/specs/senior-analyst/spec.md) | Что считается правильной работой. Формальные MUST/SHALL | ~10 минут |
| [`openspec/changes/TEMPLATE/proposal.md`](openspec/changes/TEMPLATE/proposal.md) | Шаблон любой новой задачи | справочно |

## 🚀 Как пользоваться

### Как аналитик

1. Прочитай `openspec/project.md` — контекст роли.
2. Прочитай `openspec/AGENTS.md` — правила работы.
3. Сверяйся со `specs/senior-analyst/spec.md` при ревью своей работы.
4. Для каждой новой задачи — копируй `changes/TEMPLATE/proposal.md` в `changes/CHG-XXXX/proposal.md` и заполняй.

### Как тимлид / команда

- Используй `spec.md` как **quality gate** для ревью работы аналитика.
- Ссылайся на конкретные Requirement'ы в обсуждениях: «это нарушает API Design § Спецификация до реализации».
- Используй шаблон `proposal.md` как единый формат постановки задач.

### Как ИИ-агент

- Загрузи `openspec/project.md` и `openspec/AGENTS.md` как системный промпт.
- Следуй формальным требованиям из `specs/senior-analyst/spec.md`.
- При работе над задачей — создавай `changes/<id>/proposal.md` по шаблону.
- Валидируй каждый сгенерированный артефакт через сценарии из `spec.md`.

## 🧭 Ключевые принципы

1. **Spec-first, code-second.** Нет спеки — нет задачи.
2. **Трассируемость важнее скорости.** Каждое требование имеет ID, источник и путь до реализации.
3. **Источник истины — документация, а не память.**
4. **Неопределённость — это баг.** «Примерно так» → открытый вопрос с владельцем и сроком.
5. **Один источник требований — один владелец.**
6. **Границы — часть профессионализма.**
7. **Прозрачность статуса — обязательна.**

Подробнее — в [`openspec/project.md`](openspec/project.md).

## ✅ Definition of Done

Задача считается закрытой, когда:

- [ ] Требования зафиксированы и согласованы с владельцем
- [ ] Acceptance criteria написаны и проверяемы (Given/When/Then)
- [ ] API-спецификация (если применимо) — в репозитории, прошла ревью
- [ ] ER-модель / миграции (если применимо) — согласованы с DBA
- [ ] BPMN/UML-диаграммы (если применимо) — читаемы и приложены
- [ ] Матрица трассируемости обновлена
- [ ] Открытые вопросы закрыты или переданы с владельцем и сроком
- [ ] Команда в курсе: демо / запись / заметка в общем канале

## ⚠️ Антипаттерны

- ❌ Спецификация «на словах» или в личке
- ❌ Требования без владельца и источника
- ❌ API «как получилось», без сверки со стайлгайдом
- ❌ ER-модель без учёта сценариев чтения
- ❌ Статус «в работе» три недели без апдейтов
- ❌ Согласие на всё подряд в ущерб своим задачам
- ❌ Молчание о рисках «чтобы не тревожить команду»
